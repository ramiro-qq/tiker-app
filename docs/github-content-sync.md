# GitHub 内容同步

本功能同步资料库数据，不会把应用源码目录作为 Git 工程推送。GitHub 授权、仓库绑定、内容同步是三个独立状态。

## 使用

1. 在「设置 → 同步与备份」连接 GitHub 并绑定有写入权限的仓库。
2. 点击「预览并启用同步」，检查目标仓库、默认分支、资料数量和附件问题。
3. 选择加入已有远程资料库，或将当前本地资料库单独上传。加入已有库时会比较双方内容；初次没有共同历史，不会把任一端缺少的资料直接当成删除。
4. 确认后开始双向同步。「立即同步」可主动检查；暂停后本地编辑仍保存。
5. 有冲突时比较上次、本地和远程版本，选择版本、保留两份，或编辑合并正文。所有冲突处理完毕后才写回该批内容。

首次启用采用仓库默认分支并固定该分支；资料保存在 `tiker/<libraryId>/`，保留仓库其他文件。分支保护或权限策略阻止写入时会显示错误，不强制更新分支。

本机资料库身份保持固定，加入已有库只改变远程同步目标。更换 GitHub 账号或仓库后需要重新预览，避免将旧同步基线用于新目标。

## 内容与本地保存

同步文档正文、目录、标签、收藏、已归档剪藏、稳定探知消息和材料，以及登记的附件。密钥、OAuth Token、模型配置、偏好、设备路径、运行中的模型任务和发送队列不上传。

资料库数据迁移到当前资料库下 `.tiker/content.json`。剪藏归档使用同目录的 `archives.json`；运行中的剪藏队列和模型设置仍留在本机。旧 localStorage 内容只迁移一次，保留原始迁移备份。其他资料库不会反复导入旧全局资料。

前端尚未确认保存的修改有按资料库隔离的本机恢复记录。界面显示「正在保存」或失败原因；失败时可重试或导出内容备份，不以乐观界面状态宣称已保存。浏览器预览不代表桌面持久化或真实 GitHub 同步。

## 双端差异与恢复

以最近成功同步的基线比较本地和远端实体。不同资料的修改自动合并；独立字段尝试合并；同一正文不同修改、删除与修改相遇、目录关系冲突需要处理。更新时间只用于显示和记录，不用于决定正文胜负。

删除记录保留在同步协议中，防止长期离线设备将旧资料自动复活。缺失附件、读取失败和初始化空状态不等同于主动删除。

远端每批变化形成一个真实 Git commit。分支在提交期间推进时重新比较，始终不强推。网络失败、限流和权限失败保留本地资料；请求超时后重新核对远端。同步日志和事务记录用于中断恢复；基线损坏、远端历史重写或清单删除需重新核对。

「查看版本历史」读取当前资料库的真实远程提交。恢复历史版本前备份本地，将历史内容作为新的本地修改参与后续同步，不重写远程历史。

## 附件与归档文件

附件内容以散列命名并校验，其他设备重建本机预览引用。同步不上传文件授权 ID 或绝对路径。单附件上限为 50 MiB；缺失、不可读或超限附件会列明，可显式排除。排除后其他设备仅保留资料信息，不具备该文件内容；原文件不会删除。第一版不接入 Git LFS。

归档正文以文档记录为准。受管理的 Markdown 导出记录指纹；外部文件与记录出现分歧时阻止同步并提示处理，避免悄悄上传旧正文或覆盖外部修改。应用编辑写回前保留原始文件版本。不会自动扫描资料库目录上传任意文件。

出现外部文件冲突时，先保存双方副本，再重新导入外部版本，或恢复归档文件后继续同步；当前版本不自动合并外部编辑器的文件修改。

## 调度

2／4／10 秒表示修改后的合并等待时间，不是固定推送频率；连续修改最长约 30 秒进入一次调度。后台定期检查远程变化，并对网络故障退避。应用关闭后不持续运行同步，下次打开继续处理本地待同步内容。

## 开发与验收

前端队列与调用约束：`npm run test:sync`。现有 GitHub、资料库和探知回归继续运行。Rust 测试包含合并、删除标记、目录冲突、协议校验和本机 HTTP Git Database 接口测试；检查生产构建、Clippy 和 `npm run check:focus-styles`。

本轮隔离浏览器验证使用临时 IPC 替身，检查首次启用、冲突编辑、远端正文刷新、保存失败与重试、鼠标及键盘聚焦。它不能替代真实 GitHub、多设备和平台断电测试。真实仓库需要用户在桌面应用中通过首次预览启用；测试过程不自动上传用户现有资料。
