# GitHub 内容双向同步方案（待确认）

日期：2026-11-16。本文为实现前评审方案，不代表功能已实现或已向远端上传数据。

## 1. 目标与现状

实现桌面应用资料的双向增量同步：本地编辑先可靠保存，联网后与 GitHub 合并；另一台设备可恢复内容；冲突不得静默覆盖。

当前存储并不集中：

- `src/features/Library.tsx` 将资料节点、HTML 正文、标签、收藏等写入 `tiker.library.v1` localStorage。
- `src/features/Learning.tsx` 将探知会话写入 `tiker.learning.v1`，归档时另写资料索引和 Markdown 文件。
- `src-tauri/src/clip_tasks.rs` 将剪藏任务和类目写入应用数据目录的 `clips.json`。
- `src-tauri/src/file_preview.rs` 将附件授权 ID 映射到本机绝对路径；仅同步授权 ID 无法在其他设备打开附件。
- GitHub 模块仅有账号授权、仓库管理和绑定，不存在内容传输与同步基线。

因此必须先建立统一的内容存储和写入入口，不能只递归上传设置中的目录。

## 2. 技术选择

建议使用 Rust 同步引擎 + GitHub Git Database REST API，复用现有 OAuth 和系统钥匙串；每批差异形成一个 Git commit，不要求用户安装 Git。

比较方案：

| 方案 | 收益 | 代价 | 决策 |
| --- | --- | --- | --- |
| Git Database API 批量提交 | 复用现有 HTTP/OAuth，整批版本可追踪 | 需要实现实体差异合并和请求节流 | 推荐 |
| 内嵌 Git 库 | 可复用 Git 对象与历史处理 | 引入原生依赖；Git 文本合并仍不能解决应用实体和附件冲突 | 暂不采用 |
| 整库 ZIP/JSON 备份覆盖 | 单向备份简单 | 双端编辑难以合并，容易整库覆盖 | 不作为同步方案 |

默认采用绑定仓库的默认分支，首次启用后固定分支名；远端区域为 `tiker/<libraryId>/`。只修改应用管理的区域，保留 README 和其他文件。分支受保护、权限不足或策略阻止直接提交时明确失败，不绕过规则；可更换可写分支。

## 3. 同步范围

默认纳入：

- 资料库：真实文件夹、文档正文、标题、层级、标签、收藏。
- 已归档剪藏：链接、标题、摘要、类目、标签、已有笔记，以及恢复所需的稳定内容。
- 探知：已保存的消息和材料、会话标题；不在其他设备自动恢复模型调用。
- 已导入应用的 PDF、图片、文本、表格等附件原文件，以及已归档 Markdown。

仅本地保存：OAuth/API Key、模型配置、模型选择偏好、剪藏要求与设置、设备路径、窗口主题、阅读位置、缓存、日志、运行中的任务和发送队列。现有探知“要求描述”不进入新存储协议，也不传给模型。

不自动收集目录里任意文件：只纳入应用登记的内容，目录中额外文件需通过导入加入。附件先复制为应用管理的副本，保留用户原文件；缺失或无法读取的原附件列为待处理，不把它当作删除，也不宣称完整同步。

第一版单附件上限建议为 50 MiB（产品限制，低于远程大文件边界）。超限资料继续本地保存并在同步状态中列明；用户可明确将其排除。第一版不包含 Git LFS。

## 4. 统一本地持久化与迁移

每个资料库分配稳定 `libraryId`，每个实体使用稳定 ID。建立 Rust `content_store`，以资料库内 `.tiker/` 管理原子快照、内容对象与迁移记录。前端通过 IPC 读取、按实体提交补丁，并订阅变更事件；不再由多个页面写整份 localStorage 数组。

本地事务必须同时保存：实体变化、删除标记、递增 revision、待同步状态。附件对象先完成落盘与校验，再提交索引。保存失败时不得更新为“已保存”。同步基线、冲突原始版本和事务日志保留在本机，绝不上传钥匙串或设备路径。

迁移流程：

1. 备份原 localStorage 导出、`clips.json` 和原有索引，校验后一次性导入当前资料库。
2. 验证实体数量、ID、正文、附件可读性和关联关系；损坏数据停止迁移并保留源数据。
3. 标记迁移完成，切换新写入入口；旧数据只作为恢复备份，不再作为并行写入源。
4. 旧全局资料和剪藏仅迁移一次到升级时的当前资料库；以后新建资料库独立存储。原 GitHub 绑定只作为该当前资料库的待启用目标。

文档记录保存原始 HTML/Markdown 和格式类型，不做有损转换。归档 Markdown 作为同一文档的文件呈现，不建立第二份独立正文；文件写回走统一事务。外部修改已管理文件时重新导入为本地 revision；与当前编辑器未保存内容不一致则保留两份待处理。外部改名、删除或缺失先提示，不推断为应用删除。

## 5. 远程结构与身份

```text
tiker/<libraryId>/
  manifest.json            # 协议版本、资料库 ID、实体清单与内容引用
  library/<entityId>.json   # 单个资料/文件夹及正文
  clips/<entityId>.json     # 单个已归档剪藏
  learning/<sessionId>.json # 会话稳定内容
  attachments/<hash>       # 按内容散列复用附件
  tombstones/<entityId>.json
```

远程路径使用 ID 和内容散列，显示标题存于实体中，避免重名、非法文件名、重命名误判。远端清单作为结构索引，实体文件的实际内容参与校验和比较；网页直接编辑合法实体后可被检测，不能只信旧清单散列。结构或引用损坏时停止应用该远端快照。

一个同步绑定由仓库 ID、分支、libraryId、远端路径共同确定。新设备可选择加入远程已有资料库并采用其 libraryId。更换仓库、分支或本地资料库必须切换独立基线、清除旧任务的写入资格；迟到响应不能覆盖新绑定。

## 6. 三方比较与冲突规则

比较三个版本：上次成功同步的基线 B、本地当前版本 L、远程快照 R。比较内容与字段，不用更新时间决定胜负。

| 相对 B 的变化 | 行为 |
| --- | --- |
| 都未改动 | 跳过，不创建空提交 |
| 仅 L 改动 | 上传本地修改 |
| 仅 R 改动 | 校验后应用远端修改 |
| 两边最终相同 | 直接收敛 |
| 双端修改不同实体 | 自动合并 |
| 同一实体修改不同独立字段 | 三方字段合并；合并后验证目录、引用和类型约束 |
| 同一正文或同一字段改成不同值 | 生成冲突，不按时间覆盖 |
| 一端删除，另一端未修改 | 传播删除标记 |
| 一端删除，另一端修改 | 删除/修改冲突，保留可恢复内容 |
| 文件夹删除，另一端新增/修改子项 | 作为关联冲突处理，不自动丢弃子项 |
| 附件双端变更 | 不合并二进制，选择版本或保留两份 |

正文（HTML/Markdown）第一版视为完整字段，不做逐行自动合并。重命名和移动保留 ID；合并后形成目录环、丢失父节点或标题冲突时也需处理。

冲突界面展示基线、本地、远程内容，提供“使用本地”“使用远程”“保留两份”；正文可编辑为最终版本。选择版本前备份另一版本。保留两份生成新 ID，并处理对应引用。一个资料库有未解决冲突时暂停整批写回，允许继续本地编辑，解决后重新取最新版本比较，不能沿用过期决定。

删除标记第一版不自动清理，避免长期离线设备复活旧资料。空 localStorage、读取失败、文件缺失、首次同步无记录均不得推断为用户删除。

## 7. 首次启用

绑定仓库和启用同步分开表示。已有绑定升级后展示“待首次同步”，读取远端并给出预览后由用户启用。

- 远端无 Tiker 数据：预览纳入范围、附件问题与目标可见性，确认后上传本地快照；不触碰远端其他文件。
- 远端有 Tiker 资料库：选择加入已有资料库或将当前资料库作为独立资料库上传。
- 加入已有库且本地也有内容：没有共同基线时按“双方新增”合并；同 ID 同内容去重，同 ID 不同内容进入冲突，同名不同 ID 保留两份。不能从任一端的缺失推断删除。
- 支持“从远端恢复”为替代流程：先备份本地内容，明确预览将被替换的数据后确认执行。
- 空仓库：创建首个提交和分支，再建立应用清单；处理初始化竞争。协议版本高于当前客户端时只提示升级，不写回。

若首次启用后始终没有共同基线，或基线丢失，重新进入安全首次合并；远端分支被删除或历史重写、manifest/libraryId 改变时暂停并要求重新核对，不自动当作空库上传。

## 8. 单轮同步与并发安全

1. 捕获稳定本地 revision 和绑定 generation，读取远端分支 HEAD H，并按 H 读取完整快照。
2. 三方比较，生成不可变合并计划；冲突或附件阻塞项先进入待处理。
3. 下载远端需要的对象到暂存区，检查大小、散列、格式、路径和所有引用，不创建符号链接，不允许路径越界。
4. 若有远端写入，上传变更 blob，以 H 的 tree 为 base 构建新 tree、以 H 为父提交创建 commit C，`force: false` 更新分支；远端仅有变化时不创建额外提交。
5. 远端并发推进导致非快进拒绝时，重新读取并合并，最多自动重算 3 次；持续竞争显示稍后重试，绝不强推。
6. 取得本地事务锁，检查 revision 是否仍等于捕获值；若期间用户或后台任务写入，保留新修改并重新比较，不能整库覆盖。
7. 通过预写事务日志完成本地原子切换与基线更新；新修改继续标记待同步。仅当本地与已确认远端快照一致且无未处理项时显示“已同步”。

远端提交成功但本地落盘失败时，日志保留目标 commit 和旧基线，重试时识别既有提交并继续恢复，不重复导入。请求超时后不能假设提交失败：先重读分支、检查提交关系及目标内容。启动时先恢复未完成事务再执行下一轮同步。

本地编辑和后台剪藏均使用同一内容服务；网络请求期间不长期持有存储锁。同步应用远端内容后向所有页面发变更事件，当前编辑器基于 revision 处理，不能用内存旧值回写覆盖。

## 9. 自动同步与状态

- 本地内容修改后可靠落盘，原 2/4/10 秒设置作为变更合并等待时间；持续输入时最长 30 秒调度一次。每次变更不必请求 GitHub。
- 启用后、启动后、恢复网络或窗口重新激活时检查远端；应用运行且启用同步时每 60 秒轻量检查，支持条件请求和退避；无本地变化也能接收远端更新。
- 每资料库只允许一轮同步；重复触发合并调度。关闭应用不阻塞退出，待同步状态已持久化，下次继续。
- 网络故障指数退避；限流遵守 GitHub 返回的等待信息。401 转重新授权，403 区分权限/限流/策略，仓库不可访问或只读时保留本地和绑定并明确报错。
- 设置展示：未启用、待首次同步、待上传/待下载、同步中、已同步、待处理冲突、离线、同步失败、已暂停，以及最近成功时间和未同步数量。
- 提供“立即同步”“暂停/恢复”“查看差异/处理冲突”。授权状态与内容同步状态分开。
- “自动记录间隔”改为“修改后自动同步”，说明秒数是等待合并修改的时间；版本历史取真实 Git commit。历史恢复以当前新修改重新同步，不回退远端分支。

## 10. 模块与实施顺序

1. **内容存储和迁移**：新增 `src-tauri/src/content_store/`、`src/services/content.ts`；接入 Library、Learning、clip_tasks 和归档入口；迁移与离线保存可独立验收。
2. **纯差异引擎**：新增 `src-tauri/src/content_sync/merge.rs`、协议和删除标记类型；用固定快照测试合并、冲突、层级约束。
3. **远端传输和恢复**：扩展 `github_client.rs` 的受控认证请求能力，新增同步 remote/engine/state 模块；令牌不暴露给前端。
4. **首次启用和冲突界面**：新增 `src/services/sync.ts` 与同步组件，接入 Settings；可完成手动双向同步与冲突闭环。
5. **自动调度和真实验收**：加入后台触发、轮询、错误恢复；更新 README 和 GitHub 文档。

同步 IPC 限定为 `sync_status`、`sync_preview`、`sync_enable`、`sync_now`、`sync_pause`、`sync_conflicts`、`sync_resolve`，由后端绑定确定目标，不允许前端提交任意网络 URL、路径或令牌。预览与冲突决定关联本地 revision、远端 HEAD 和绑定 generation，过期时重新计算。

## 11. 验收标准

- 老数据迁移前后数量、正文和附件一致，迁移中断可重试，损坏源数据不覆盖。
- 双设备分别验证单端新增/修改/删除、独立实体合并、同文冲突、删除对修改、文件夹删除对子项新增、附件冲突和重命名。
- 验证首轮双方有内容、旧固定 ID 冲突、新设备恢复、无共同基线、协议不兼容。
- 验证远端竞争、上传超时但实际成功、限流、权限拒绝、网络中断、磁盘满、程序崩溃恢复、同步时继续编辑及后台任务写入。
- 验证远端手动修改、损坏文件、缺少附件、目录穿越、分支删除、历史重写及切换绑定后迟到响应。
- 无变化不生成提交；远端其他文件保持完整；断网可继续编辑；有未处理项不显示完整同步成功。
- 所有新增界面遵守 AGENTS.md，无 outline 或模拟焦点框，保留键盘操作，检查鼠标、Tab 和弹框自动聚焦的计算样式。
- 执行针对性 Rust/TypeScript 测试、现有 GitHub/资料库/学习回归、`npm run check:focus-styles`、`npm run build`、Cargo test 和 Clippy。使用 HTTP 测试服务验证失败路径，使用专门测试仓库和两个隔离数据目录验证真实远端，不以 mock 代替实机结论。

## 12. 本轮待确认的推荐默认值

确认本方案即采用：双向同步；默认分支下独立 Tiker 目录；同步文档、已归档剪藏、稳定探知内容和可用附件；正文冲突人工选择并可保留两份；2/4/10 秒合并等待、60 秒远端检查；单附件 50 MiB 上限；第一版不含 LFS 和正文逐行自动合并。
